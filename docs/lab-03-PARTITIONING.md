## Часть 1. RANGE PARTITIONING по дате
**Ответы на вопросы:**
1. Запись с `created_at = '2026-09-10 12:00:00'` попадет в партицию `events_2026_09_10`.
2. Запись с `created_at = '2026-09-11 00:00:00'` попадет в партицию `events_2026_09_11`.
3. При попытке вставить запись за `2026-09-12` произойдет ошибка (PostgreSQL выдаст `no partition of relation "events" found for row`), так как подходящая партиция не создана.
4. Граница `TO` в PostgreSQL всегда **не включает** указанное значение (Exclusive). Это сделано для избежания пересечений диапазонов: (`>= '2026-09-10' AND < '2026-09-11'`).

## Часть 2. Partition pruning
**Ответы по плану EXPLAIN ANALYZE:**
* **Сколько партиций проверил PostgreSQL:** 1 партицию.
* **Какая нужна запросу:** `events_2026_09_10`.
* **Удалось ли исключить остальные:** Да (остальные 2 партиции даже не открывались).
* **Где видно pruning:** В плане запроса сканируется только физическая таблица `events_2026_09_10`, остальные отсечены на этапе планирования (Partition Pruning).

**Почему второй запрос (по `event_type`) обращается ко всем партициям?**
Ключ партиционирования — `created_at`. База данных не знает, в какие дни происходили клики (`event_type = 'click'`). Поэтому ей приходится сканировать все существующие партиции.

## Часть 3. RANGE PARTITIONING по числовому значению
**Ответ:**
Для запроса `WHERE price >= 100 AND price < 500` PostgreSQL просмотрит **только одну** партицию: `products_medium`. Так как диапазон запроса (100-499) полностью укладывается в границы партиции `products_medium` (100-1000).

## Часть 4-5. LIST PARTITIONING и DEFAULT
* Какая партиция используется для `B2B`: `customers_b2b`. Остальные отсекаются, так как это точное совпадение (List). Отличие от Range в том, что здесь нет диапазонов, есть строгий список категорий.
* **Зачем нужна DEFAULT partition:** Чтобы собирать данные, которые не подошли ни под одно из явно заданных правил (например, 'VIP'). Без нее `INSERT` упадет с ошибкой.
* **Проблемы DEFAULT:** Если неизвестных значений будет много, DEFAULT партиция разрастется до невероятных размеров, убив смысл партиционирования. Кроме того, из DEFAULT партиции нельзя будет "вытащить" данные в новую партицию напрямую без переливки.

## Часть 6. HASH PARTITIONING
**Ответы:**
1. Данные распределились равномерно (разница между партициями минимальна, обусловлена хэш-функцией).
2. **Почему полезен:** Идеально для балансировки I/O нагрузки и распределения данных по разным дискам, когда нет явного критерия для Range или List.
3. **Отличие от RANGE:** Мы не управляем тем, куда физически ляжет строка. Это решает хэш-алгоритм от значения ключа.
4. **Почему плохо для удаления старых данных:** Данные перемешаны. Нельзя просто сделать мгновенный `DROP TABLE events_2023`, придется делать долгий и тяжелый `DELETE FROM events WHERE created_at < ...`, что вызовет блокировки и раздувание базы (bloat).

## Часть 7. Выбор стратегии партиционирования
* **Сценарий A (Логи за 3 года):** `RANGE` по дате. Позволит мгновенно удалять старые логи командой `DROP TABLE` без блокировок.
* **Сценарий B (B2C, B2B):** `LIST` по типу. Идеально ложится на дискретный набор категорий для частых фильтраций.
* **Сценарий C (Равномерное по user_id):** `HASH`. Обеспечит равномерное "размазывание" горячих пользователей по физическим файлам диска.
* **Сценарий D (Заказы диапазоном дат):** `RANGE` по `created_at`. Максимальная польза от Partition Pruning при аналитике по месяцам.
* **Сценарий E (Платежи по странам):** `LIST` по коду страны. Позволит изолировать данные разных стран на разных физических серверах (важно для законов о хранении данных).

## Часть 8-9. Партиционирование и индексы
**Ответы:**
1. Партиционирование и индексы работают на **разных уровнях**. Pruning отсекает ненужные таблицы (файлы) целиком. Индекс внутри оставшейся нужной таблицы быстро находит нужную строку, избегая `Seq Scan`.
2. Почему комбинация лучше: Pruning сужает область поиска до миллиона строк вместо миллиарда, а B-Tree индекс мгновенно находит нужную запись среди этого миллиона.
3. Почему сам по себе partitioning не решает проблему `event_type`: Партиционирование решает проблему *управления жизненным циклом данных* и фильтрации по ключу партицирования. Для быстрого поиска по не-ключевым полям всегда нужен индекс.

**Шаг 1-4. Выбор:**
* **Таблица:** `core_ticket` (Билеты).
* **Ключ:** `created_at` (Дата создания).
* **Стратегия:** `RANGE` (По месяцам или дням).
* **Обоснование:** Таблица билетов растет постоянно, старые билеты за прошлые года в оперативном приложении не нужны (их можно архивировать и удалять `DROP PARTITION`). Запросы аналитики почти всегда идут в разрезе временных периодов.
* **Польза от pruning:** Запросы выручки за текущий месяц не будут сканировать данные за прошлые годы.

**Шаг 6. Проверка запросов (до и после):**

*Запрос: `SELECT * FROM core_ticket WHERE created_at >= '2023-11-01' AND created_at < '2023-12-01'`*

* **Scan (без Pruning - обычная таблица):** Seq Scan on core_ticket_old - 160.569 ms
* **Scan (с Pruning - партицированная таблица):** Seq Scan on core_ticket_2023_11 - 0.033 ms

## Контрольные вопросы
1. **Что такое partitioning?** Разделение одной большой логической таблицы на несколько маленьких физических таблиц (файлов) средствами СУБД.
2. **Чем отличается от индекса?** Индекс — это структура данных (B-tree) для быстрого поиска строки. Партиционирование — это физическое разбиение самих данных. Индексы строятся внутри партиций.
3. **Стратегии в PostgreSQL:** `RANGE`, `LIST`, `HASH`.
4. **Когда RANGE?** Данные имеют естественный порядок и диапазоны (даты логов, цены), необходимо массово удалять старые данные (Data Lifecycle).
5. **Когда LIST?** Дискретные категории (Страны, Статусы, Роли).
6. **Когда HASH?** Нужно равномерно распределить данные для балансировки нагрузки без логического разделения.
7. **Как выбрать ключ?** Ключ должен присутствовать в `WHERE` подавляющего большинства тяжелых запросов.
8. **Что такое partition pruning?** "Обрезка партиций". Механизм оптимизатора запросов, который на этапе планирования исключает из сканирования партиции, которые заведомо не содержат искомых данных.
9. **Почему pruning может не сработать?** Если запрос не содержит фильтрации по partition key, либо используются функции, не являющиеся IMMUTABLE (запрещающие предрасчет).
10. **Можно ли использовать индексы с partitioning?** Да, это обязательно для эффективной работы.
11. **Что если партиции нет?** Операция `INSERT` завершится фатальной ошибкой.
12. **Зачем создавать заранее?** Чтобы избежать простоев системы и потерь данных, если скрипт создания (job) однажды упадет из-за сбоя сети или прав.
13. **Почему автоматизировано?** Человеческий фактор неизбежно приведет к забытой партиции 1 января, что вызовет простой системы (Downtime).
14. **Логирование vs Alerting?** Логи просто пишутся в файл (никто их не читает 24/7). Alert — это активное уведомление (SMS, TG) дежурному инженеру о критической проблеме.
15. **Что такое recovery alert?** Уведомление о том, что проблема решена (зеленый статус). Позволяет инженеру понять, что вставать ночью и чинить базу больше не нужно.
16. **Почему нельзя спамить alert?** Инженеры выработают "alert fatigue" (слепоту к уведомлениям) и проигнорируют реально важную аварию. Уведомление шлется 1 раз, далее система молчит до починки.
17. **Всегда ли ускоряет?** Нет. Если запрос не использует ключ партиционирования, базе придется делать `Append` сканирований по всем партициям, что будет работать медленнее одной большой таблицы.
18. **Проблемы неправильного размера?** Слишком мелкие (тысячи партиций) — планировщик запросов сойдет с ума и начнет тормозить на этапе парсинга. Слишком крупные — деградирует автовакуум и не поместятся индексы в RAM.
