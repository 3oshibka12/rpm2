# Шардирование PostgreSQL: Router и Consistent Hashing

## 1. Выбор данных для шардирования
**1. Какую сущность вы выбрали?**
Для шардирования выбрана сущность `Ticket` (Билеты) из собственного сервиса кинотеатра.

**2. Какое поле используется как shard key?**
В качестве ключа шардирования выбран `customer_email`.

**3. Почему выбран именно этот ключ?**
Для обеспечения Data Locality (локальности данных). Если шардировать билеты по email, все билеты одного пользователя гарантированно окажутся на одном физическом сервере. Это позволяет обслуживать тяжелые запросы вида "Получить историю билетов пользователя" локально на одном шарде, избегая дорогих Cross-Shard Join-ов и Broadcast-запросов (когда роутеру нужно опрашивать весь кластер).

**4. Насколько равномерно он будет распределять данные?**
Электронные адреса обладают высокой кардинальностью. Прогон строки email через криптографическую хэш-функцию обеспечит равномерное псевдослучайное распределение, минимизируя риск "перекоса" данных (Data Skew).

**5. Какие запросы вашего сервиса используют этот ключ?**
* Поиск билетов по пользователю (`GET /tickets/?customer_email=...`)
* Создание нового билета (`POST /tickets/`)

## 2. Запуск нескольких PostgreSQL
В `docker-compose.yml` были развернуты 4 независимых экземпляра PostgreSQL (`shard_0`, `shard_1`, `shard_2`, `shard_3`). Для работы с ними в `cinema_conf/settings.py` были зарегистрированы соответствующие алиасы `DATABASES`.

## 3. Реализация простого Router
В коде проекта был реализован Python-маршрутизатор, определяющий целевую базу по алгоритму `hash(key) % N`. Базовые справочные данные (Сеансы, Фильмы) были сдублированы во все шарды для соблюдения консистентности Foreign Keys.

## 4. Распределение данных
В базы данных было физически загружено 100 000 билетов с использованием Django `bulk_create` (с разделением партий по целевым шардам).

Фактический подсчет записей в СУБД:
```text
shard_0 -> 33413 записей (33.41%)
shard_1 -> 33384 записей (33.38%)
shard_2 -> 33203 записей (33.20%)
```

**Вывод:**
* Данные распределились равномерно (~33.3% на каждый экземпляр БД).
* Заметного дисбаланса нет (разница в доли процента).
* Микро-дисбаланс не является проблемой, так как архитектура серверов закладывается с запасом емкости дисков.

## 5. Что произойдёт при добавлении нового shard?
К системе был добавлен 4-й шард. Формула изменилась с `hash(key) % 3` на `hash(key) % 4`.

```text
hash(key) % N переместит: 74801 записей (74.80%)
```

**Вывод:**
Добавление всего одного нового PostgreSQL сервера привело к фатальной проблеме: изменился делитель N, а значит, остаток от деления поменялся почти для всех ключей. Это приводит к необходимости физического перемещения около 75% всех существующих данных по сети на новые сервера. В HighLoad-проектах это означает гигантские I/O нагрузки, блокировки таблиц и многочасовой простой (Downtime).

## 6. Реализация Consistent Hashing
Для решения проблемы был реализован алгоритм Consistent Hash Ring. Вместо деления по модулю, серверы и ключи проецируются на единое кольцо (через 100 виртуальных узлов для балансировки). Запись принадлежит первому серверу, встретившемуся на кольце по часовой стрелке.

## 7. Сравнение стратегий
Эксперимент с добавлением 4-го шарда был повторен с использованием Consistent Hashing.

Перемещено:
* `hash(key) % N`: **74.8 %**
* `Consistent Hashing`: **27.68 %**

**Объяснение:**
1. **Почему результаты отличаются?** При подходе `% N` меняется функция вычисления для *всех* ключей. При Consistent Hashing функция не меняется, новый шард просто вклинивается на кольцо, перехватывая на себя только часть "территории" своих соседей.
2. **Почему Consistent Hashing позволяет уменьшить объём?** Данные перемещаются только от тех соседей, чей сектор на кольце сузился. Остальные 75% данных кластера остаются нетронутыми.
3. **Что произойдёт, если добавить ещё один shard?** При добавлении 5-го шарда потребуется переместить только `1/5` часть данных (около 20%).
4. **Что произойдёт, если удалить shard?** Данные с удаленного шарда (25%) плавно "стекут" на его ближайшего соседа по кольцу. Пересчитывать и переносить остальные 75% данных не придется.

## 8. Итог
* **Shard (Шард)** — физический экземпляр БД, хранящий горизонтальный срез общих данных.
* **Shard key** — колонка, по значению которой маршрутизатор определяет целевой шард.
* **Router** — механизм на уровне приложения или прокси, перехватывающий запросы и вычисляющий целевой шард.
* **hash(key) % N** — базовый алгоритм маршрутизации, зависящий от точного количества шардов.
* **Проблема при изменении N** — эффект "лавины": изменение числа серверов ломает маршруты для почти 100% данных, вызывая катастрофический решардинг.
* **Consistent Hashing решает проблему** путем размещения хэшей серверов на кольце. При изменении узлов ребалансируется только `1/N` часть кластера.
* **Вывод для сервиса:** Для сервиса кинотеатра категорически выбран Consistent Hashing с виртуальными узлами (Virtual Nodes), так как это единственный способ безопасно и без простоев масштабировать кластер баз данных при росте нагрузки.

## Вопросы для самопроверки

1. **Что такое shard?** Отдельная база данных, на которой хранится только часть таблицы (горизонтальное масштабирование).
2. **Что такое shard key?** Поле, используемое для вычисления местоположения строки в кластере.
3. **Почему нельзя просто случайно распределять записи?** Это убьет возможность поиска. Если запись распределена случайно (Round-Robin), при SELECT-запросе роутеру придется опрашивать все шарды кластера одновременно (Scatter-Gather), что крайне неэффективно.
4. **Как работает hash(key) % N?** Берется хэш от ключа (переводится в число) и вычисляется остаток от деления на текущее количество серверов `N`.
5. **Почему изменение количества shard’ов является проблемой?** Математика остатка от деления перестраивает маршруты для подавляющего большинства ключей (например, 75% при переходе с 3 на 4 шарда), требуя остановки кластера для переноса терабайтов данных.
6. **Что такое Consistent Hash Ring?** Алгоритм, проецирующий ключи данных и адреса серверов на общее кольцо хэшей. Ключ принадлежит первому серверу, найденному по кольцу по часовой стрелке.
7. **Почему при добавлении shard’а не приходится переносить все данные?** Добавляемый сервер забирает только ту часть хэш-кольца (данных), которая относится к его новому "соседу", не трогая остальные участки кольца.
8. **Что такое virtual nodes и зачем они нужны?** Виртуальные узлы — это проецирование одного физического сервера на кольцо несколько раз (сотни точек). Это устраняет проблему неравномерных секторов и обеспечивает идеальный баланс данных.
9. **Может ли Consistent Hashing гарантировать идеальное распределение нагрузки?** Без виртуальных узлов — нет. С виртуальными узлами — да, распределение стремится к идеально ровному.
10. **Что произойдёт, если один shard станет значительно более загруженным остальных?** В кластере возникнет "Hot Spot" (Горячая точка). Для решения проблемы этому серверу можно либо добавить мощностей (Vertical Scaling), либо изменить вес (увеличить/уменьшить количество его виртуальных узлов на кольце).
