# Лабораторная работа 6
# Что происходит с backend-сервисом после шардирования

## 1. Вспоминаем архитектуру
В рамках нашего сервиса кинотеатра была шардирована таблица `core_ticket` (Билеты).
В качестве **shard key** выбрано поле `customer_email`. 
Маршрутизация (Router) вычисляет хэш от email покупателя и направляет запрос в один из целевых шардов кластера.

## 2. Single-Shard Query (Запрос к одному шарду)
**Запрос из сервиса:**
```sql
SELECT * FROM core_ticket WHERE customer_email = 'john.doe@example.com';
```
**Объяснение:**
Данному запросу не нужно обращаться к другим шардам, так как в условии `WHERE` явно указан shard key (`customer_email`). Роутер на стороне бэкенда (или прокси-сервера) хэширует строку `'john.doe@example.com'`, понимает, что все данные этого пользователя лежат, например, строго на `Shard 1`, и отправляет SQL-запрос только туда. Это идеальный сценарий шардирования, работающий с максимальной эффективностью.

## 3. Агрегирующий запрос
**Запрос из сервиса (Выручка по статусам билетов):**
```sql
SELECT status, SUM(price) FROM core_ticket GROUP BY status;
```
**Ответы:**
1. **Можно ли выполнить такой запрос только на одном shard?** Нет. Каждый шард содержит только свою треть проданных билетов. Один шард не знает о финансовой картине всей системы.
2. **Где должны объединяться результаты?** Роутер (backend) должен отправить этот запрос параллельно во **все** шарды (Scatter). Затем backend должен дождаться ответов, загрузить их в свою оперативную память (RAM) и выполнить финальную математику (Gather) — сложить суммы, полученные от каждого шарда.
3. **Что происходит со временем выполнения при увеличении количества shard’ов?** Время выполнения увеличивается и становится равным времени ответа **самого медленного** шарда в кластере. Плюс добавляются накладные расходы на сетевые вызовы и финальную агрегацию в оперативной памяти бэкенда.

## 4. JOIN между shard’ами
В нашем сервисе `Ticket` связан внешним ключом с `Showtime` (Сеанс).
**Запрос из сервиса:**
```sql
SELECT t.id, t.price, s.start_time 
FROM core_ticket t
JOIN core_showtime s ON t.showtime_id = s.id
WHERE t.customer_email = 'user@example.com';
```

**Рассмотрение ситуации (если бы Сеансы и Билеты лежали на разных шардах):**
1. **Что произойдёт?** Выполнить классический `JOIN` невозможно, так как базы физически изолированы (на разных серверах). PostgreSQL на Shard 0 ничего не знает про таблицы на Shard 1.
2. **Можно ли выполнить такой JOIN обычным SQL-запросом?** Нет, стандартный SQL внутри одной БД этого не позволит (без использования тяжелых расширений вроде `postgres_fdw`).
3. **Какие данные пришлось бы передавать?** Бэкенду пришлось бы сделать `SELECT showtime_id FROM ticket` на Shard 0, сохранить ID в память, а затем сделать `SELECT * FROM showtime WHERE id IN (...)` на Shard 1, после чего "склеивать" объекты прямо в коде Python. Это катастрофически медленно (N+1 проблема).
4. **Как выбрать shard key для локального JOIN?** В нашей архитектуре мы решили эту проблему путем дублирования (репликации) справочной таблицы `Showtime` на все шарды. Таким образом, JOIN всегда выполняется локально внутри одного шарда.

## 5. ORDER BY + LIMIT
**Запрос из сервиса (Последние 20 проданных билетов глобально):**
```sql
SELECT * FROM core_ticket ORDER BY created_at DESC LIMIT 20;
```
**Объяснение:**
Недостаточно получить 20 записей с одного шарда, потому что самые "свежие" билеты могут находиться на любом из серверов. Бэкенд вынужден отправить запрос `ORDER BY created_at DESC LIMIT 20` во **все** шарды. Если шардов три, бэкенд получит $20 \times 3 = 60$ записей. Затем код на Python должен сам отсортировать эти 60 записей по дате в памяти и отрезать финальные 20 (`top 20`). Это называется Distributed Sort.

## 6. Отказ одного shard
**Ситуация: Shard 2 вышел из строя.**
1. **Какие данные становятся недоступны?** ~33% всех билетов (те, чей email хэшировался на Shard 2).
2. **Какие endpoint’ы перестанут работать?** Перестанет работать глобальная аналитика (агрегации), так как не хватает части данных. Пользователи, закрепленные за Shard 2, не смогут войти в профиль, купить билет или посмотреть историю.
3. **Продолжит ли работать остальная часть сервиса?** Да, остальные 66% пользователей на Shard 0 и Shard 1 смогут полноценно покупать билеты и пользоваться системой.
4. **Что должен делать backend?** При обращении к упавшему шарду backend должен ловить таймаут соединения, корректно обрабатывать исключение и возвращать клиенту `503 Service Unavailable`, не "роняя" всё приложение (изоляция сбоя).
5. **Как повысить отказоустойчивость?** Использовать репликацию для каждого шарда (Primary-Replica). При падении Primary Shard 2, трафик автоматически переключится на Replica Shard 2.

## 7. Hot Shard (Горячий шард)
**Ситуация: Shard 2 обрабатывает 75% запросов.**
В нашей системе (shard key = `customer_email`) такое маловероятно из-за равномерного хэширования, однако:
**Возможные причины:** Появление аномально активного пользователя (например, B2B-клиент, корпоративный аккаунт по продаже билетов, скрипт-бот), который делает тысячи запросов в секунду со своего email.
**Ответьте:** Равное количество строк на шардах не означает равную нагрузку, потому что 99% пользователей могут купить билет и забыть, а 1% пользователей будет запрашивать свои билеты по API каждую секунду. Вся CPU/IO нагрузка от этих частых SELECT-ов ляжет исключительно на тот шард, где лежат их записи (эффект Hot Spot).

## 8. Итоговый анализ shard key
**Подходит ли `customer_email` для собственного сервиса?**
Да, подходит, но с оговорками, зависящими от бизнес-целей.

* **Плюсы:** Идеально работает для клиентских сценариев (Личный кабинет пользователя). Запросы вида "Мои билеты" становятся эффективными Single-Shard запросами.
* **Минусы:** Глобальные запросы (отчеты администратора, пагинация последних проданных билетов по всем кинотеатрам) становятся распределенными (Scatter-Gather).
* **Проблемные операции:**
    * **JOIN:** Очень сложен, если связанные сущности не лежат на том же шарде (требует денормализации или справочной репликации).
    * **Aggregation & ORDER BY:** Требуют выгрузки промежуточных результатов в RAM бэкенда.
    * **Балансировка:** Перенос данных при расширении кластера вызывает остановки (если не используется Consistent Hashing).

**Вывод:**
Если бы система проектировалась заново с упором на аналитику и отчеты по кинотеатрам, возможно, логичнее было бы выбрать `cinema_hall_id` или `tenant_id` в качестве shard key. Однако, так как кинотеатр — это B2C сервис, где 90% нагрузки создают обычные пользователи, запрашивающие свои билеты, ключ `customer_email` (или `user_id`) является оптимальным компромиссом.

## Вопросы для самопроверки

1. **Чем single-shard query отличается от distributed query?** В single-shard запрос идет точно в одну целевую БД (быстро, локально). В distributed query роутер не знает, где данные, поэтому опрашивает все шарды параллельно и собирает результат в памяти.
2. **Почему JOIN между shard’ами сложнее обычного?** СУБД изолированы. Нельзя объединить таблицы SQL-запросом. Бэкенду приходится делать отдельные SELECT'ы к разным базам и вручную сопоставлять объекты в коде.
3. **Как выполнить COUNT(*) по всем shard’ам?** Отправить `SELECT COUNT(*)` на каждый шард отдельно, дождаться ответов, и сложить полученные числа в оперативной памяти приложения.
4. **Почему ORDER BY ... LIMIT требует объединения результатов?** Глобальный топ не равен локальным топам. Нужно получить `LIMIT` записей с *каждого* шарда, слить их в общий массив на бэкенде, отсортировать и отрезать финальный `LIMIT`.
5. **Что произойдёт при отказе одного shard?** Данные этого шарда станут недоступны. Глобальные агрегации начнут выдавать ошибку. Пользователи других шардов не пострадают.
6. **Что такое hot shard?** Узел кластера, на который ложится аномально высокая I/O или CPU нагрузка из-за перекоса распределения запросов (например, туда попал слишком активный пользователь).
7. **Почему выбор shard key влияет на JOIN?** Если связанные данные (Пользователь и его Заказ) имеют один shard key, они физически лежат на одном сервере, и JOIN работает локально. Если ключи разные — JOIN невозможен на уровне БД.
8. **Какие операции особенно плохо подходят для распределённых данных?** Глобальные агрегации (SUM, AVG), глобальная сортировка с пагинацией (ORDER BY OFFSET), Cross-Shard JOIN.
9. **Что произойдёт при изменении количества shard’ов?** Изменится логика маршрутизации. Часть данных окажется на "неправильных" серверах, и их придется физически переносить по сети (Решардинг).
10. **Чем шардирование отличается от репликации?** Репликация копирует *одни и те же* данные на несколько серверов для надежности. Шардирование режет *разные* данные на куски для распределения объема и нагрузки на запись.
11. **Может ли шардирование сделать отдельный SQL-запрос быстрее?** Да, если это Single-Shard запрос на огромной таблице. Благодаря шардированию таблица на целевом узле стала в N раз меньше, а значит B-Tree индексы стали компактнее и помещаются в кэш процессора, ускоряя поиск.
