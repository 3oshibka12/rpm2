### Задание 4. EXPLAIN ANALYZE
**Вопросы:**
1. **Чем EXPLAIN отличается от EXPLAIN ANALYZE?** `EXPLAIN` просто строит план и показывает примерные (estimated) оценки на основе статистики БД. Запрос при этом не выполняется. `EXPLAIN ANALYZE` реально выполняет запрос, замеряет фактическое время и показывает реальное количество обработанных строк (actual).
2. **Почему EXPLAIN ANALYZE может выполняться значительно дольше?** Потому что происходит физическое чтение данных с диска и их обработка, тогда как `EXPLAIN` работает только с метаданными.
3. **Чем отличаются предполагаемые и фактические значения?** Предполагаемые (estimated) рассчитываются планировщиком на основе статистики, которая может быть устаревшей. Фактические (actual) — это точное число строк, которые подошли под условие в момент выполнения.

### Задание 5. Последовательное сканирование (Sequential Scan)
**Вопросы:**
1. **Какой тип сканирования используется?** `Seq Scan`.
2. **Почему выбирается Sequential Scan?** Условие `amount > 0` охватывает почти всю таблицу (или ее огромную часть).
3. **Всегда ли Sequential Scan — это плохо?** Нет, не всегда.
**Вывод:** Если запрос должен вернуть большую часть таблицы (например, > 10-20% строк), `Seq Scan` эффективнее индекса. Чтение данных с диска большим последовательным блоком работает быстрее, чем миллион случайных скачков по индексу (Random I/O).

## Часть 8. Bitmap Scan

### Задание 10
**Вопросы:**
1. **Что делает Bitmap Index Scan?** Он проходит по индексу и составляет битовую карту (карту памяти), отмечая, на каких физических страницах диска лежат нужные нам строки. Сами данные из таблицы он не достает.
2. **Что делает Bitmap Heap Scan?** Он берет готовую битовую карту, идет в саму таблицу (Heap) и читает только нужные страницы блоками.
3. **Почему используется Bitmap Scan вместо Index Scan?** Это компромисс. Обычный `Index Scan` читает данные по одной строке, что вызывает медленный Random I/O. Если строк нужно вернуть довольно много, `Bitmap Scan` собирает адреса всех строк, группирует их и читает физические блоки с диска более оптимально.

## Часть 9-11. Составные индексы (Composite Index)

### Задание 11-13
**Вопросы (Задание 12):**
1. **Какой вариант эффективнее?** Составной индекс `(user_id, status)` отработал эффективнее, чем объединение двух отдельных индексов (BitmapAnd).
2. **Всегда ли составной индекс лучше?** Нет. Он занимает больше места на диске и его сложнее переиспользовать в других запросах.
3. **От чего зависит выбор?** Если колонки почти всегда запрашиваются вместе — нужен составной. Если по отдельности — лучше два разных.

**Вопросы (Задание 13 - Порядок колонок):**
1. **Как порядок влияет на использование?** Индекс работает как телефонный справочник (Фамилия, Имя). Индекс `(created_at, user_id)` нельзя использовать для быстрого поиска только по `user_id`, так как данные отсортированы сначала по дате.
2. **Почему это разные индексы?** У них разная корневая структура сортировки.
3. **Какой индекс лучше?** Первым в составном индексе нужно ставить поле с проверкой на равенство (`user_id = 123`), а вторым — поле с диапазоном (`created_at > ...`).

## Часть 14. Index Only Scan

### Задание 16
**Вопросы:**
1. **Отличие Index Only Scan:** При `Index Scan` база ищет адрес в индексе, а потом идет в таблицу (Heap) за данными. При `Index Only Scan` она не обращается к таблице вообще.

## Часть 23. Финальный вопрос

### Задание 30. Почему нельзя индексировать всё?
1. **Размер:** Индексы занимают много места на диске и в RAM. Проиндексировав всё, мы раздуем БД в несколько раз.
2. **Падение скорости записи:** Каждый INSERT/UPDATE/DELETE заставляет БД синхронно перестраивать все привязанные индексы. Операции записи сильно замедлятся.
3. **Ресурсы на обслуживание:** Большое количество индексов требует больше ресурсов процессора на процессы VACUUM и сборку мусора.
4. **Реальная польза:** Индексы на колонках с низкой селективностью будут проигнорированы планировщиком в пользу Seq Scan, что делает их бессмысленными.
